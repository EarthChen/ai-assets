  • common-tech-stack.md · uv / pnpm 硬约束
🔍 展开：几条关键准则的设计动机
  • Think Before Coding：针对 LLM "先写再说"倾向——错误假设导致的返工远大于开口问一句。
  • Simplicity First：针对过度工程——200 行能写 50 行即重写，不为单次使用加抽象。
  • Surgical Changes：针对"顺手改"——仅动该动之处，让 review 能聚焦。
  • Fail loud：针对静默失败——无法确定成功则明说，与 silent-failure-hunter agent 互为表里。
  • 不可变性 CRITICAL：原地修改产生隐藏副作用，要求创建新对象而非原地改。
  • uv / pnpm 硬约束：防 agent 混用 pip/conda/npm/yarn 导致 lockfile 不一致、环境不可复现。

工程工作流链

从需求到交付的完整闭环，显式化为可执行步骤序列，避免跳步返工。

grill-with-docs
对齐需求+领域模型 → to-spec
沉淀 spec → to-tickets
拆 tracer-bullet 票 → implement
按票实现 → code-review
双轴评审
🔍 展开：链路前端的两个配套 skill（需求尚未成型阶段）

wayfinder · 规划超大块工作

当目标模糊且路径不可见时，不直接冲向终点，而是把目标画成 issue tracker 上的"决策票地图"——每张票解决一个决策而非切片构建，逐个解决直到路径清晰。

  • 设计核心：规划而非执行——地图是索引不是存储，决策只活在它自己的票里；有 fog of war 机制（刻意不画看不清的部分）。
  • 调用分两模式：chart the map（建图）与 work through the map（推进）。每 session 至多解决一张票（research 票除外）。
  • 定位：对 to-spec/to-tickets 的前置补充——后者处理"需求清晰、可拆票"的场景，wayfinder 处理"需求太大太糊、连怎么走都不确定"的场景。

research · 后台调研子代理

对一手信源（官方文档、源码、spec、一方 API）做调查，写成 markdown 存入仓库，每条结论标信源。设计核心是后台运行、主 agent 继续干活——调研是耗时 I/O，阻塞主 agent 不值得。

11

grilling：整个工作流的根节点

在动手之前，通过 relentless 追问达成共识。grill-me、grill-with-docs 均为它的上层包装。

单问单答 · 逐枝推进

一次只问一个问题，等反馈再继续，禁一次抛多个。针对 LLM 趋于一次性产出多步方案的倾向。

事实查环境 · 决策问用户

事实（filesystem、工具可查）由 agent 主动探查；决策（取舍、偏好）必须逐个抛给用户。

为每个问题提供推荐答案

把对话从"从头想"变为"判断对错"，判断成本远低于创造成本。

未达共识不动手

针对"边问边做"倾向——未达共识的实现建立在未对齐的假设上，返工成本高。

为何是根节点：工作流链的后续环节（to-spec、to-tickets、implement、code-review）均建立在"需求已对齐"的前提下；而"需求对齐"这个前提，正是由 grilling 达成。跳过 grilling 直接进 to-spec，会把未澄清的假设带入 spec，返工成本随环节推进指数增长。

三套 skill 的 TDD 哲学对比

本地另一套 superpowers 与开源项目 gsd（Get Shit Done）也含 TDD 与 code-review，但设计哲学差异显著：

维度 mattpocock tdd superpowers gsd tdd
基调 方法论约束，定义循环纪律 铁律执行，反驳合理化借口 流水线化，gate 强制
核心机制 seam（公共边界）+ vertical slice + 反模式清单 "NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST" gate 强制 RED/GREEN/REFACTOR commit
Refactor 归属 不在循环内，归 code-review 在循环内 在循环内（可选 gate）
质量保障 反模式清单可诊断失败模式 "红旗清单"指向删除重来 gate validation 检查 commit 存在
🔍 展开：seam 的本质——只测公共边界、不测实现细节

测试在公共接口上观察行为，而非深入内部或 mock 内部协作者。依据：代码可整体重构而行为不变，测试不应随实现变动而断。

  • seam 作为"观察行为而不深入内部"的公共边界，测试只在 seam 上写。
  • 要求先与用户确认 seam 再写测试，把"测什么"从 agent 自行判断提升为显式契约。
  • 将 implementation-coupled（mock 内部协作者、测私有方法、通过旁路验证）列为反模式——诊断特征是"重构时测试会断但行为没变"。

差异：superpowers、gsd 均强调"先写测试"与"测试质量"，但未将"测边界不测细节"作为可诊断的失败模式与契约机制显式约束。

三套 skill 的 code-review 对比

维度 mattpocock code-review superpowers gsd
结构 单 skill，双轴并行 两 skill 拆分：请求 + 接收 独立 agent，命令 spawn
评审轴 双轴（Standards + Spec）并行，不合并 单轴 checklist 单轴对抗式
严重程度 四级（CRITICAL/HIGH/MEDIUM/LOW） 三级 两级（BLOCKER/WARNING）
反馈接收 未单独规定 禁表演式同意、先验证再实现、YAGNI 检查 不负责接收，专注对抗式找问题
三者的根本差异在设计哲学：mattpocock 防"评审遗漏或轴间污染"；superpowers 防"反馈被表演式接受或盲目实现"；gsd 防"评审流于表面或漏掉跨文件问题"。三者并存的价值——个人/小团队可用 mattpocock 的轻量纪律，团队协作可用 superpowers 的请求/接收拆分，大型项目可用 gsd 的流水线化 gate 强制。

anysearch vs 内置 web_search / fetch_content

二者并非替代关系，而是能力分层互补，差异源于定位不同。

维度 anysearch 内置 web_search / fetch_content
架构形态 外部 CLI skill，调用第三方 API 平台原生工具
搜索能力 通用 + 16 个垂直域（带 sub_domain 结构化参数） 仅通用搜索
并行能力 batch_search 多意图并行 单次单查询
内容提取 extract 返回 Markdown，覆盖 SPA/JS 渲染页 支持 YouTube/视频帧/GitHub，对 SPA 有 Gemini 回退
隐私边界 查询发往第三方，标注"不得用于含敏感信息的查询" 查询走平台自身，无第三方泄露面
分工依据：内置工具的优势在于零依赖、零配置、始终可用（快速事实查询、富媒体提取）；anysearch 的优势在于专业领域的召回质量与多意图并行（垂直域能返回结构化数据如股票代码、CVE、DOI）。global-instructions.md 规定"anysearch 首选、内置回退"——按查询性质分流而非按偏好绑定。

skills 与 rules 分离的原因

常见困惑：python-patterns（skill）与 rules/python/（rule）均在处理 Python，为何不合并？

rules = 约束

永远生效或按文件类型生效，agent 必须遵守。约束不宜写入 skill（可能根本不触发）。

skills = 脚本

按场景触发，提供做事步骤。步骤不宜写入 rule（会无差别占用上下文）。

两者职责正交，合并将模糊边界。此即 common-testing.md 中以"Skill Support"引用 TDD 而非将 TDD 步骤内联的原因。

项目文档管理：为何不用记忆系统

grilling、domain-modeling、to-spec、to-tickets 共同产出一套仓库内可见的文档体系——针对 agent 记忆系统失败模式的设计选择。

CONTEXT.md

领域术语表，记定义与同义反义，不记实现。

docs/adr/

架构决策记录，三条件满足才创建。

.scratch/<feature>/

本地 issue tracker：spec.md + issues/NN-*.md 票。

docs/agents/

skill 运行时配置，由 setup 一次性创建。

🔍 展开：记忆系统的三个失败模式 → 为何用仓库内文档
  1. 记忆不可 review：记忆库对人类不可见，无法审查 agent 记了什么、记对没有。仓库内文档可读、可 review、可 git diff——决策被错误记录时人类能在 review 中发现。
  2. 记忆检索是概率性的，决策调用需要确定性：记忆按相关性检索，可能漏检索或检索到过时条目。但术语定义、ADR 决策是"调用即需准确"的——用文件而非记忆，是"读文件"（确定性）取代"问记忆"（概率性）。
  3. 记忆跨 session 不稳定，文档跨 session 稳定：记忆常按 session 隔离或随清理丢失；跨 session 的决策需稳定可复现。仓库内文档随 git 持久化，任何 session、任何 agent、任何人类读同一个文件得到同一信息。

职责边界：文档承担"长期记忆"职责（显式、可见、可审查）；会话偏好（如回答风格）不在文档职责内，随 session 生灭。需跨 session 持久的才落文档。

架构层：两层分工

architect · 系统级

整体设计、可扩展性、技术决策、ADR。

输出：高层架构图 + 组件职责 + 数据模型 + API 契约。

用于"做架构决策"

code-architect · 特性级

分析现有代码的模式与约定，给出可执行的施工图。

输出：具体文件路径 + 接口 + 数据流 + 构建顺序。

用于"这个功能在现有代码里怎么落地"

分两层的原因："做架构决策"与"在现有代码中落地一个特性"属于性质迥异的任务——前者抽象度高、需全局权衡；后者需读懂现有约定并产出可执行施工图。合并为单一 agent 将导致要么能力不足、要么职责过载。
19

评审层：按语言与技术栈分兵 + 统一输出契约

按栈分设 reviewer 而非单一通用 reviewer，因各技术栈关注点不同：FastAPI 的 async 正确性、Java 的 JPA/N+1、TypeScript 的类型安全、ML 的训练可复现性。

严重程度分级（统一评审输出契约）

级别 含义 动作
CRITICAL 安全漏洞或数据丢失风险 BLOCK · 合并前必须修复
HIGH Bug 或显著质量问题 WARN · 合并前应修复
MEDIUM 可维护性顾虑 INFO · 考虑修复
LOW 风格或轻微建议 NOTE · 可选
设计价值：不同 reviewer agent 关注点不同，若无统一分级，各自输出无法被下游（PR 是否可合并）机械判断。分级后，"无 CRITICAL/HIGH 则通过"成为可机读的合并门槛，agent 不需再人工权衡"这个问题严不严重"。

设计原理：为何用 agent 而非 skill

核心差异在触发模型与上下文归属。

skill · 加载到主上下文

场景触发的脚本，被主 agent 加载到上下文、由主 agent 自己执行。

上下文不隔离——执行后仍在同一上下文继续。

agent · 委派给独立子 agent

委派判断力的角色，在上下文干净的子 agent 内独立完成、结果回流。

上下文隔离——主 agent 不深入细节，只收结果。

🔍 展开：边界——轻量局部走 skill，全仓系统走 agent

为何用 agent 而非 skill：agent 适用于需上下文隔离与独立判断力边界的场景——refactor-cleaner 要跑 analyzer、grep 全仓、查 git 历史、逐项判 SAFE/CAREFUL/RISKY，这些探查的中间上下文若涌入主 agent 会淹没其推理，写成 agent 则隔离在子 agent 内。code-simplifier 同理——需独立判断"哪些简化能简化、哪些是过度设计"，需独立判断力边界以免与主 agent 的实现上下文串混。

反观 tdd（skill）内的 refactor 阶段是轻量、局部、在测试保护下的一步重构，主 agent 自己加载 skill 即可执行，无需委派。

边界：轻量局部重构走 skill，全仓系统重构走 agent。

为何子 agent 而非全塞入主 agent：子 agent 的价值不在于"多实例并行"，而在于上下文隔离与职责边界——主 agent 保留全局视角与决策权，将需要深度专注的子任务委派至上下文干净的子 agent，结果回流。主 agent 不被某个深任务的细节淹没，子 agent 也不被全局上下文干扰。

并发执行：git worktree 的实际使用

用 git worktree 而非 stash + branch-switching——stash 易丢失、切换需重装依赖。worktree 让每个并行任务拥有独立工作目录与依赖环境。 

~/work/<org>/
├── main-repo/                  # 主仓库
│   └── backend/                # submodule, .git 指向 modules
│       ├── service-a/          # nested submodule, master 分支 (主工作树)
│       ├── service-b/          # nested submodule, master 分支 (主工作树)
│       └── service-c/          # nested submodule, master 分支 (主工作树)
└── worktree/                   # worktree 目录, 置于主仓库外
    └── feature-X/              # 以分支名命名, 特性的统一工作区
        ├── service-a/          # service-a 的 worktree, feature-X 分支
        └── service-b/          # service-b 的 worktree, feature-X 分支
🔍 展开：四条约定 + 设计动机
  • 置于仓库外：防嵌套污染文件搜索与 IDE 目录扫描。
  • 一分支一 worktree：一分支不能同时检出两个 worktree。
  • 依赖与 env 不共享：node_modules//.venv//.env 各 worktree 重装。
  • 合并后清理：git worktree remove + prune，不留残留。

为何以分支名命名顶层目录？同一特性常涉及多个服务——一个 feature-X 可能同时改 service-a/b/c。以分支名为顶层，把该特性涉及的所有服务 worktree 放在同一目录，形成统一工作区。agent 操作该特性时只需进入一个目录即可访问全部相关服务，这对 agent 的文件搜索、跨服务重构、一致性检查都是必要的。

与子 agent 的互补：子 agent 隔离的是推理上下文，worktree 隔离的是文件系统与依赖环境，两者共同支撑并发工作流。

小结：三个核心设计判断

① 职责分层而非能力堆砌

rules（约束）/ skills（工作流）/ agents（判断力委派）三层正交，各层触发模型不同（常驻 / 场景 / 委派）。

不合并为单一"能力池"，目的是让每类资源仅在合适的时机占用上下文。

② 单一真相源与平台适配层

install.py build 将同一份源码转换为各平台所识别的格式。

Cursor 的 .mdc + globs、Claude 的 paths、Codex 的 AGENTS.md 嵌入。一处修改，四处生效。

③ 防御性闭环

TDD 保证编写时正确，修复层保证失败被接住，评审层保证交付前被审查。

每一环节均有明确的 skill 或 agent 负责，不存在无覆盖的环节。

该体系本身是活的——install.py 负责部署，skills/ 与 agents/ 为实际内容，rules/ 为约束底座。
